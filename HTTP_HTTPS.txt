What is HTTP?

HTTP (HyperText Transfer Protocol) is a protocol used for communication between client and server.

👉 Data is sent in plain text.

Client → HTTP Request → Server
Client ← HTTP Response ← Server

❌ Problem with HTTP

Data can be read

Data can be modified

Data can be stolen

Example risk:

Passwords

Tokens

Credit card data

What is HTTPS?

HTTPS (HTTP Secure) is HTTP + Security.

👉 Uses SSL/TLS encryption.

Client → Encrypted Request → Server
Client ← Encrypted Response ← Server

Key Difference (Simple Table)
HTTP	HTTPS
Data is plain text	Data is encrypted
Not secure	Secure
Port 80	Port 443
No certificate	Requires SSL/TLS certificate
Vulnerable to attacks	Protected from attacks
How HTTPS Works (Very Basic)

Client connects to server

Server sends SSL certificate

Browser verifies certificate

Secure encrypted connection created

Data transferred safely

👉 This happens before HTTP requests start

Example (Java System)
HTTP (Insecure)
POST /login
username=reddy&password=1234


Anyone sniffing network can see this ❌

HTTPS (Secure)
POST /login
<encrypted data>


Data is unreadable ✅

Why HTTPS is Important in System Design?

Trust between client and server

Used for:

What is HTTPS Handshake?

The HTTPS handshake is the process where client and server establish a secure (encrypted) connection before any HTTP request/response is sent.

👉 Goal:

Verify server identity

Agree on encryption keys

Start secure communication

HTTPS Handshake – Step by Step
🔹 Step 1: Client Hello

The client (browser / app) starts the connection.

Client sends:

Supported TLS versions

Supported encryption algorithms (cipher suites)

Random number (Client Random)

Client → Server : "I want to connect securely"

🔹 Step 2: Server Hello

Server responds with:

Chosen TLS version

Chosen cipher suite

Server Random

SSL/TLS Certificate (Public Key)

Server → Client : Certificate + encryption choice

🔹 Step 3: Certificate Verification (Client Side)

Client checks:

Certificate is issued by a trusted CA

Certificate is not expired

Domain name matches

❌ If invalid → connection rejected
✅ If valid → continue

🔹 Step 4: Key Exchange (Secret Creation)

Client:

Generates a Pre-Master Secret

Encrypts it using server’s public key

Sends it to the server

Client → Server : Encrypted secret


👉 Only server can decrypt it (has private key)

🔹 Step 5: Session Key Generation

Both client & server now independently generate:

Session Key (symmetric key)

They use:

Client Random + Server Random + Pre-Master Secret

🔹 Step 6: Secure Connection Established

Handshake completed

All communication now encrypted using session key

Client ↔ Server : Encrypted HTTP data

What Happens AFTER Handshake?

Normal HTTP starts — but securely.

GET /users/1
Authorization: Bearer token


👉 Data is encrypted, unreadable to attackers

Why Use Public + Symmetric Keys?
Key Type	Used For
Public/Private	Secure key exchange
Symmetric Key	Fast data encryption

👉 Performance optimized + secure
